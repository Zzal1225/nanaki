# 기록 1만 건에서 모든 화면이 3.3초 — 동기화 "겹쳐 받기"가 매번 전부 다시 받고 있었다

> 2026-10-24 · PR #117 · 다시 방문 홈 3.26초 → **0.93초**

## 문제

기록 1만 건(3년치)을 넣고 재 보니 홈·기록 탭·설정까지 **모든 화면이 약 3.3초**였고, 메인 스레드가 50ms 넘게 막힌 시간(긴 작업)의 합이 1.4초였다. 이 달 기록(약 270개)만 읽는 홈까지 느린 것이 이상했다.

측정 조건: 모바일 화면, 크롬 스로틀링(CPU 4배, 느린 4G), 5회 가운데 값. 자세한 방법은 [performance.md](../performance.md) "step4 41".

## 원인을 찾은 방법

1. **이 달만 읽는 화면도 느리다** → 화면별 조회가 아니라 모든 화면이 공유하는 비용을 의심했다.
2. **로컬에서 IndexedDB에만 1만 건을 넣고 CPU 프로파일** → 앱 코드는 100ms 안팎. 기록 수 자체는 원인이 아니었다. (나중에 보니 재현이 안 된 이유가 있었다: 직접 넣은 줄은 `updated_at`이 오래된 값이라 아래 "겹침 구간" 밖이었다.)
3. **같은 밀도로 300개만 넣은 비교군**을 같은 CI 실행에서 쟀다 → 1.1초, 긴 작업 0. 차이 2.2초는 "전체 개수" 때문인데 화면이 읽는 양과는 무관했다.
4. **3.3초 ≈ 동기화 최대 대기 3초 + 그리기**라는 숫자에서 동기화를 의심했다.

## 원인

동기화는 서버에서 "마지막으로 받은 시각(커서) 이후에 바뀐 줄"만 받는다. 그런데 늦게 커밋된 저장을 놓치지 않으려고 **늘 커서보다 60초 앞부터 다시 받는** 안전장치가 있었다. 측정용 1만 건은 0.6초 안에 한꺼번에 넣어 모두 그 60초 안에 있었고, 화면을 열 때마다 1만 건(3.5MB)을 다시 받아 IndexedDB에 다시 썼다.

측정 데이터만의 문제가 아니다. 실제 사용자도 **백업 불러오기로 수천 건을 한 번에 넣으면**, 다음 기록을 쓸 때까지 화면을 열 때마다 같은 일을 겪는다.

## 해결

커서를 처음 본 기기 시각을 함께 저장하고, **60초가 지난 뒤 시작한 겹쳐 받기를 한 번 마치면 커서를 "확정"**한다. 확정된 뒤에는 커서 바로 뒤부터만 받는다. 새 기록이 들어와 커서가 앞으로 가면 다시 확정 전으로 돌아간다.

왜 안전한가: 그 받기가 시작될 때 서버 시각은 이미 커서 시각 + 60초를 넘었으므로, 60초 안에 끝나는 저장은 모두 끝나 있었고 그 받기가 가져왔다. 기기 시계는 "얼마나 지났나"에만 쓴다(뒤로 돌리면 겹쳐 받기를 더 할 뿐이라 안전).

고르지 않은 대안: 겹침을 60초 → 5초로 줄이기(간단하지만 5초 안에 넣은 대량 불러오기는 여전히 매번 다시 받음), 측정 데이터만 현실적으로 바꾸기(사용자 문제가 남음).

## 결과

| 다시 방문 (가운데 값 · 긴 작업) | 고치기 전       | 고친 뒤       | 300개 비교군 |
| ------------------------------- | --------------- | ------------- | ------------ |
| 홈                              | 3262ms · 1406ms | **929ms · 0** | 920ms · 0    |
| 기록 탭                         | 3256ms · 1479ms | **974ms · 0** | 982ms · 0    |
| 보고서(올해)                    | 3277ms · 1503ms | **980ms · 0** | 911ms · 0    |

1만 건이 300개와 같은 속도가 됐다. 300개도 겹침 안의 줄을 다시 받고 있어서 1.1초 → 0.92초로 빨라졌다. 단위 테스트 4개(60초 전후, 커서가 앞으로 가면 다시 확정 전, 늦게 끝난 저장, 예전 사본).

## 배운 것

- "N건이라 느리다"는 가설은 **같은 밀도의 작은 비교군**으로 가를 수 있다. 비교군이 없었으면 3.3초가 앱 시작 비용인지 기록 수 비용인지 알 수 없었다.
- CI 서버는 실행마다 속도가 10~15% 흔들린다. 전후는 실행끼리가 아니라 **같은 실행 안의 비교군**과 견준다.
