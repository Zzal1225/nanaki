# 로그인 LCP가 로고가 아니라 2.4초의 "는" 글자로 잡혔다 — 투명도 0에서 시작하는 등장 애니메이션

> 2026-10-27 · PR #141 · 로그인 Lighthouse 88 → **98**, 같은 로고를 쓰는 홈 76 → **92**

## 문제

배포 주소 Lighthouse 90+를 목표로, 로그인 화면이 처음부터 받던 JS를 353KiB에서 206KiB로 줄였다(#140). 그런데 같은 조건 3회가 95 / 87 / 88점으로 들쭉날쭉했다. 87·88점 실행의 보고서를 보니 LCP 요소가 화면 위쪽의 큰 "nanaki" 로고가 아니라 **"나는 나를 키운다" 문구의 "는" 한 글자**였고, 관측 LCP가 2.4~3.2초였다.

측정 조건: 배포 주소, Lighthouse 13.5.0 모바일 simulate, 매번 새 프로필·캐시 비움, 3회. 자세한 방법은 [performance.md](../performance.md#배포-주소-lighthouse-90-목표-2026-10-27).

## 처음 생각 → 틀림

이전 측정에서도 "는"이 LCP로 잡힌 적이 있어, **웹 글꼴이 늦게 와서** 글자를 다시 그린 시점이 잡힌 것이라고 기록해 두었었다. 그렇다면 느린 환경일수록 더 자주 나와야 한다.

## 원인을 찾은 방법

Lighthouse 보고서는 마지막 LCP 요소 하나만 보여 준다. 그래서 Playwright로 배포 주소를 열고, 페이지가 시작될 때 `PerformanceObserver({ type: 'largest-contentful-paint', buffered: true })`를 붙여 **LCP 후보가 바뀌는 순서를 모두** 기록했다.

| 조건                   | 결과                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| 느린 망 + CPU 4배 감속 | 3회 모두 로고(크기 3,724)                                                                               |
| 제한 없음 (빠른 환경)  | 5회 중 첫 번째만 로고. 나머지 4회는 **로고가 후보에 아예 없고** "나"(1.7초) → "나"(1.9초) → "는"(2.4초) |

예상과 반대였다. 글꼴이 **빨리** 올 때 문제가 생겼다.

## 원인

로고는 등장 애니메이션이 `opacity: 0`에서 시작해 0.6초 동안 나타난다. **Chrome은 처음 그릴 때 투명도 0인 요소를 LCP 후보에서 빼고, 나중에 보이게 돼도 다시 세지 않는다.**

- 글꼴이 늦게 오면: 글꼴이 도착해 로고를 다시 그릴 때는 이미 보이는 중이라 후보가 된다
- 글꼴이 빨리 오면: 로고는 투명할 때 한 번 그려지고 끝이라 후보에서 빠진다. 그다음 "처음 그려지는" 글자는 문구 애니메이션(색 바꿈·접힘)이 1.7~2.4초에 다시 그리는 작은 글자들이다

Lighthouse simulate는 **관측 LCP 시각 이전에 시작된 요청을 모두** 느린 4G에서 다시 계산한다. LCP가 2.4초로 밀리면 그사이 받은 JS가 전부 추정에 들어가 점수가 떨어진다. 사용자는 0.1초부터 로고를 보고 있는데도 그렇다.

## 해결

로고만 투명도 **0.01**에서 시작하는 키프레임으로 바꿨다. 눈으로는 차이가 없다.

```css
.login-wordmark {
  animation: login-up-counted 0.6s var(--login-ease-enter) 0.1s both;
}
@keyframes login-up-counted {
  from {
    opacity: 0.01;
    transform: translateY(16px);
  }
  to {
    opacity: 1;
    transform: none;
  }
}
```

고르지 않은 것: 문구·슬로건·버튼까지 모두 0.01로 바꾸기. 거의 투명한 글자가 화면에 있으면 Lighthouse 접근성의 대비 검사가 그 순간을 잡아 점수가 떨어질 수 있다. LCP가 돼야 하는 로고만 바꿨다.

## 결과

- 로컬 빌드 확인(빠른 환경 5회): 5회 모두 로고가 LCP(0.09~0.16초)
- 배포 뒤 같은 조건 3회: **로그인 88 → 98, LCP 3.81 → 2.12초**
- 로그인 뒤 앱을 열 때의 로딩 화면이 같은 로고를 써서 **홈도 76 → 92**가 됐다. 홈의 관측 LCP가 0.5초에서 0.25초로 당겨지면서, 그 뒤에 시작된 JS 요청이 추정에서 빠졌다
- 같은 원리로 기록 탭도 고쳤다. 데이터를 기다리는 동안 회색 상자만 그리던 카드를 같은 틀로 그려 두고 글자만 바꾸게 하자 75 → 92 (#143)

## 배운 것

- Lighthouse 보고서의 LCP 요소 하나만 보지 말고, **후보가 바뀌는 순서 전체**를 `PerformanceObserver`로 찍어 본다. "왜 이 요소가 LCP인가"보다 "왜 저 요소가 LCP가 아닌가"가 답이었다.
- simulate 점수는 바이트보다 **무엇이 언제 LCP로 잡히는지**에 더 민감했다. 이번 작업에서 JS를 줄인 수정(로그인 +4점)보다 LCP 요소를 바로잡은 수정(로그인 +10점, 홈 +16점, 기록 탭 +17점)이 훨씬 컸다.
- 한 번 기록해 둔 원인("글꼴이 늦어서")도 가설이다. 조건을 바꿔 다시 재 보니 반대였다.
