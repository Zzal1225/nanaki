# 로그인 화면 Lighthouse 95 → 84: 고치려다 "실제로는 안 느려졌다"를 찾음

> 2026-10-23 · 코드를 바꾸지 않기로 결정

## 문제

step3 마무리 측정에서 배포 주소 로그인 화면의 Lighthouse 성능이 step2의 95에서 **84**로, LCP가 2.6초에서 3.9초로 떨어졌다. LCP 요소는 그 사이에 바꾼 아바타 로고 그림(112px)이었다.

## 처음 생각 → 틀림

- **그림 요청이 늦게 시작한다** (측정 보고서의 Load Delay 1.76초, 45%) → `<link rel="preload">`로 미리 받기 → 로컬 79 → 80, LCP 4.5초 그대로.
- **그림을 받는 동안 JS가 막는다** → 그림을 HTML에 직접 넣기(data URI) → 79, LCP 4.5초 그대로. **요청을 아예 없앴는데도** 변화가 없었다.

## 원인을 찾은 방법

같은 로컬 production build를 Lighthouse의 두 측정 방식으로 비교했다.

| 방식            | 설명                                      | 원래 코드               |
| --------------- | ----------------------------------------- | ----------------------- |
| simulate (기본) | 가벼운 실행 기록으로 느린 환경을 **추정** | 79, LCP 4.5초           |
| devtools        | 네트워크·CPU를 **실제로 느리게** 돌림     | **97, LCP 1.6초 = FCP** |

LCP는 첫 그리기(FCP)보다 빠를 수 없다. 실제로 느리게 돌린 측정에서 LCP = FCP라는 것은, 로고 그림이 화면이 보이는 시점을 늦추지 않는다는 뜻이다. simulate는 "LCP 요소가 그림이면 그 전에 받은 JS까지 기다린 것"으로 추정하는 것으로 보인다(LCP 요소가 글자였을 때는 FCP와 같게 잡혔다).

## 결정

**코드는 바꾸지 않았다.** preload·data URI 실험은 되돌렸다. 점수를 되돌리려면 로고를 LCP 후보가 아닌 도형(SVG)으로 다시 그려야 하는데, 사용자가 보는 화면은 같고 시안과 달라질 수 있어 하지 않았다. 대신 수치와 근거를 [performance.md](../performance.md)에 남기고, 앞으로 로그인 화면 점수는 simulate 84 안팎을 기준으로 보기로 했다.

## 결과

- 사용자 경험이 바뀌지 않았음을 수치로 확인했다(devtools 97, LCP 1.6초).
- 점수만 보고 고쳤다면 이득 없는 data URI(HTML +7.5KB)나 그림 다시 그리기를 넣었을 것이다.

## 배운 것

- Lighthouse 점수가 떨어졌을 때 **"무엇이 느려졌나"보다 "정말 느려졌나"를 먼저** 묻는다. simulate와 devtools를 같은 빌드에서 비교하면 추정 오차인지 실제 회귀인지 가를 수 있다.
- 실험은 한 번에 하나씩, 되돌리기 쉽게. 두 실험 모두 수치가 꿈쩍하지 않은 것이 "원인이 아니다"의 증거가 됐다.
