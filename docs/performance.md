### 확인한 것

- 홈의 LCP 요소는 기록 12개·300개 모두 **하루 요약 줄**이다. 기록을 받아야 그려지는 요소라, 홈의 LCP는 기록 조회가 끝나야 정해진다. 20a의 가설 중 "LCP가 기록에 묶여 있다"는 확인됐다.
- 기록이 12개 → 300개가 되어도 FCP·JS 전송량은 그대로다. 전체 전송량은 102KiB 늘었는데, 300개 응답 본문(106KiB)과 크기가 비슷하다.
- 처음 가는 달로 넘기는 시간(1.2초)은 기록 요청 시간(1.2초)과 거의 같다. 캐시된 달은 24ms로, 300개를 날짜별로 묶어 그리는 데는 시간이 거의 들지 않는다.
- 5회 값의 흔들림은 첫 실행의 첫 표시(6754ms)를 빼면 1% 안쪽이다.

### 측정 방식 고침 (처음 방문 / 다시 방문)

그래서 두 가지로 나눠 잰다 ([`scripts/calendar-perf.mts`](../scripts/calendar-perf.mts), [`scripts/lighthouse.mts`](../scripts/lighthouse.mts)).

| 다시 방문 | 한 번 열어 둔 뒤 아무것도 지우지 않음 (서비스 워커·기록 사본 그대로)                                                    |

## step3 마무리: 로그인 화면 점수 하락 조사 (2026-10-23)

### 무엇이 보였나

step3 마무리 측정에서 배포 주소 로그인 화면의 Lighthouse 성능이 step2 95 → **84**(12.8.2, 3회 84 / 86 / 84), LCP 2.6초 → 3.9초로 떨어졌다. LCP 요소는 #92에서 새싹 아이콘(색 칠한 원 + 선 아이콘)을 바꾼 112px 아바타 그림이다. 12.8.2와 13.5.0 둘 다 같아서 도구 버전 차이는 아니다.

### 무엇을 해 봤나 (로컬 빌드 `npm start`, 같은 컴퓨터, Lighthouse 12.8.2 모바일, 3회 가운데 값)

| 방법                                 | simulate (기본, 추정) | devtools (실제로 느리게) |
| ------------------------------------ | --------------------- | ------------------------ |
| 원래 코드 (next/image, eager + high) | 79, LCP 4.5초         | **97, LCP 1.6초**        |
| `preload` (head에서 미리 받기)       | 80, LCP 4.5초         | (재지 않음)              |
| 그림을 HTML에 넣기 (data URI 5.5KiB) | 79, LCP 4.5초         | 96, LCP 1.6초            |

- 3회 모두 LCP 값이 같아(4.5초 / 1.6초) 흔들림 때문이 아니다.
- 그림 요청을 아예 없애도(data URI) simulate의 LCP는 4.5초 그대로였다 → 그림을 받는 방식이 원인이 아니다.
- 실제로 느리게 만든 측정(devtools)에서는 원래 코드도 **LCP = 첫 그리기(FCP) = 1.6초**다. LCP는 FCP보다 빠를 수 없으니, 실제 화면에서 로고 그림이 LCP를 늦추지 않는다.

### 결론

점수 하락은 Lighthouse 기본 방식(simulate)의 추정 때문이다: LCP 요소가 그림이면 그 전에 받은 JS까지 기다린 것으로 계산하는 것으로 보인다(글자일 때는 FCP와 같게 잡혔다). 사용자가 보는 화면은 바뀌지 않았으므로 **코드는 바꾸지 않는다** (2026-10-23 사용자 결정). preload·data URI는 실제 이득 없이 HTML·복잡도만 늘려 되돌렸다. 점수를 되돌리려면 로고를 LCP 후보가 아닌 도형(SVG)으로 다시 그려야 하는데, 사용자 경험이 같고 그림이 시안과 달라질 수 있어 하지 않았다.

- 보고서(HTML): 로컬 `private/performance/2026-10-23-login-logo-lcp/` (공개하지 않음)
- 앞으로 로그인 화면 점수는 simulate 84 안팎이 기준이다. 비교할 때 이 조사를 함께 본다.

**정리**: 기록 탭은 데이터 경로(새 출처 Supabase 연결 + 조회)가 가장 크고, 홈은 웹 글꼴과 데이터 경로가 비슷하게, 그 아래에 JS 457KiB가 모든 화면에 깔려 있다. 그래서 고치는 순서를 **데이터 경로 → 글꼴 → JS**로 정했다(처음 예상한 글꼴 → JS → 데이터 경로에서 진단 결과로 바꿈).

| 기록 탭 | 74 / 75 / 74 | 74 / 75 / 74   | 74 → **74** | 7.02 → 7.02초   |

- 이유로 보는 것: 추정 LCP는 관측된 요청 목록을 느린 망에서 다시 계산하는데, 데이터 요청은 JS를 다 받고 돌린 뒤에야 나간다. 연결을 앞당겨도 "JS 457KiB를 받는 시간"이 그 앞을 그대로 막고 있어 계산된 시각이 거의 같다. 진단에서 Supabase를 막았을 때 크게 줄어든 것은 연결이 아니라 **데이터를 기다리는 LCP(금액) 자체가 빈 화면으로 바뀌어** LCP가 첫 그리기로 당겨졌기 때문이다
- 실제 사용자(빠른 망)에게는 연결 한 번만큼 빨라질 수 있어 되돌리지 않았다. 측정 실수 하나: 첫 1단계 측정 중 같은 컴퓨터에서 단위 테스트를 돌려 CPU 지수가 3,300 → 1,985로 떨어진 실행이 섞였다. 그 측정은 버리고 아무것도 돌리지 않은 상태로 다시 쟀다(위 표)
- 다음: 데이터 경로는 "데이터를 기다리는 LCP"라 연결만으로는 안 줄어든다 → 글꼴(진단 −1.0~1.3초)과 JS(데이터 요청 앞을 막는 457KiB)를 먼저 줄인다

### 2단계: 글꼴 → 원인만 확인하고 미룸

글꼴 몫(진단 −1.0~1.3초)이 어디서 오는지 더 나눠 봤다.

- **Roboto**(구글 버튼 글자, next/font): 로그인 뒤 화면에서도 미리 받기(preload)가 걸려 있다. 이것만 막아 같은 조건 3회 → 홈 추정 LCP 6.35 → 6.14~6.20초(−0.15초), 기록 탭 6.86~7.18초, 로그인 4.14~4.22초. **흔들림 수준이라 고치지 않는다**

고칠 수 있는 길은 둘인데 둘 다 이번에는 고르지 않았다.

#### 3-1b. 로그인: 로고가 LCP로 잡히지 않던 문제

진단(Playwright, 배포 주소, `PerformanceObserver`로 LCP 후보를 모두 기록, 원인 확인용):

- 느린 망·CPU 4배: 3회 모두 로고(크기 3,724)가 LCP
- 망·CPU 제한 없이 5회: 첫 번째만 로고, **나머지 4회는 로고가 후보에 아예 없고** "나"(1.7초) → "나"(1.9초) → "는"(2.4초, 크기 546)가 차례로 LCP

원인: 로고는 등장 애니메이션이 **투명도 0**에서 시작한다. Chrome은 처음 그릴 때 투명도 0인 요소를 LCP 후보에서 빼고, 나중에 보이게 돼도 다시 세지 않는다. 글꼴이 늦게 오면 글꼴을 바꿔 다시 그리는 시점에 로고가 보이는 상태라 후보가 되지만, 글꼴이 빨리 오면(캐시가 따뜻한 서버 등) 로고는 끝까지 빠진다. 그다음 처음 "그려지는" 글자는 문구 애니메이션(색 바꿈·접힘)으로 다시 그려진 1.7~2.4초의 작은 글자다. Lighthouse는 관측 LCP 이전 요청을 모두 계산에 넣으므로, LCP가 2.4초로 밀리면 그사이 받은 것이 전부 추정에 들어간다.

해결: 로고만 투명도 **0.01**에서 시작하는 키프레임으로 바꿨다(눈으로는 같다). 문구·슬로건·버튼은 그대로 0이다. 거의 투명한 글자가 보이면 Lighthouse의 대비 검사가 그 순간을 잡아 접근성 점수가 떨어질 수 있어서다.

#### 3-2. Sentry를 첫 화면 뒤에 켜기 (모든 화면)

Sentry 브라우저 SDK(압축 약 80KiB)는 `instrumentation-client.ts`가 앱 시작 때 바로 불러와 모든 화면의 첫 화면 조각에 실려 있었다.

- 바꾼 것
  - `load` 뒤 한가할 때(`requestIdleCallback`, 최대 3초, 없으면 1초 뒤) 동적 `import()`로 받아 켠다
  - 켜지기 전에 난 오류(`error`·`unhandledrejection`)는 모아 두었다가 켜지면 보낸다(`lib/sentry/lazySentry.ts`, 단위 테스트 5개)
  - `global-error.tsx`도 Sentry를 직접 import하지 않고 같은 입구를 쓴다. 직접 import하면 본체가 다시 첫 화면 조각에 실린다
- 함정: `import('@sentry/nextjs')`로 바로 받으면 번들러가 어떤 함수를 쓸지 몰라 패키지 전체(화면 녹화 Replay·피드백 위젯 포함)를 담아 나중 조각이 **192KiB**가 됐다. 쓰는 세 함수만 정적으로 다시 내보내는 파일(`sentryBrowserEntry.ts`)을 거쳐 받으니 **78KiB**로 바꾸기 전과 같아졌다
- 분석기(②) 첫 화면 JS: 로그인 294 → **214KiB**, 홈 543 → **463KiB**, 기록 탭 572 → **493KiB**
- 감수한 것: Sentry가 켜지기 전의 화면 이동은 성능 추적에 남지 않는다. 첫 화면 성능(pageload)은 Sentry가 켜질 때 브라우저 기록을 읽어 남는다

| ------- | ------------- | ------------ | ----------- | -------------------- | --------------------- |
| 로그인  | 96 / 98 / 99  | 97 / 99 / 99 | 98 → **99** | 2.12 → **1.82초** ✅ | 201~206 → 146KiB      |
| 홈      | 87 / 92 / 92  | 94 / 94 / 97 | 92 → **94** | 3.02 → 2.68초        | 341~426 → 187~351KiB  |

- 기록 탭은 LCP(금액, 관측 0.51~0.57초)가 Sentry 요청보다 늦어 여전히 모든 JS가 추정에 들어간다

#### 3-3. 기록 탭: LCP를 데이터를 기다리지 않는 자리로

원인: 이번 달 카드는 불러오는 동안 회색 상자만 그렸다가, 데이터가 오면 큰 금액 숫자(28px)를 처음 그린다. 그 순간(관측 0.5~0.6초)이 LCP가 되고, 그 전에 시작된 JS·Supabase 요청이 모두 추정에 들어갔다(진단에서 Supabase를 막으면 2.1~2.6초였던 이유).

해결: 불러오는 동안에도 같은 카드(아이콘·타입 이름·값 자리의 흐린 줄표 "—")를 그리고, 데이터가 오면 **같은 요소의 글자만** 바꾼다. Chrome은 이미 그린 글자 요소의 내용이 바뀌는 것은 LCP로 다시 세지 않는다.

### 홈·기록 탭에서 멈춘 이유

남은 0.2~0.4초는 관측 LCP(약 0.2초) 전에 시작되는 것들이다: HTML, 렌더링을 막는 CSS(Pretendard 92조각 선언 포함 24KB), 앱 틀의 JS(LCP 전 10~18개, 187~387KiB). 더 줄이려면 아래 셋 중 하나를 해야 하는데, 모두 이 앱의 설계 원칙이나 디자인 결정과 부딪친다.

1. **앱 틀의 데이터 코드(supabase-js·zod·Dexie 약 140KiB)를 늦게 받기** → 이 앱은 오프라인 우선이라 화면을 열면 가장 먼저 기기 사본(IndexedDB)을 읽고 대기열(outbox)을 보낸다. 이 코드를 늦추면 실제 사용자, 특히 다시 방문(기기 사본에서 약 1초)과 오프라인에서 데이터가 늦게 보인다. 실험실 점수를 위해 실제 사용자의 체감을 늦추는 거래라 하지 않았다
2. **서버에서 데이터를 그려 보내기** → 화면 HTML이 사용자·데이터마다 달라진다. 지금은 화면 HTML이 한 장이라 서비스 워커 저장본으로 한 번도 안 연 화면도 오프라인에서 연다(CLAUDE.md, 2026-10-22 결정). 이 구조를 버려야 한다
3. **`font-display: optional`** → 첫 방문 화면이 기기 기본 글꼴로 보인다. 로고의 첫인상이 바뀌어 사용자가 미루기로 했다(2단계)

실제 사용자 기준으로는 관측 LCP가 세 화면 모두 0.2~0.3초(빠른 망)이고, 기기 사본이 있는 다시 방문은 홈이 약 1초에 다 그려진다. 0.2~0.4초를 더 줄이려고 위 셋 중 하나를 고르는 것보다, 오프라인 우선 설계를 지키는 쪽이 이 앱의 목적에 맞다고 판단해 여기서 멈췄다.
