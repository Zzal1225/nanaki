# 오프라인 우선: 읽기는 기기 사본에서, 쓰기는 온라인이어도 늘 사본 먼저

> 2026-10-22 · 25b(사본 동기화), 25c(쓰기 대기열)

## 상황

첫 오프라인 실험에서 연결이 끊기면 기록이 회색 자리에 멈췄다. 기록을 기기에 두고 읽어야 했다. 원칙은 이미 정해져 있었다: 기준 데이터는 서버, IndexedDB는 기기 사본, `updatedAt`은 서버가 붙이고 충돌은 마지막 저장 우선.

## 결정

### 읽기: 기기 사본(IndexedDB, Dexie)

- 사본은 **서버 줄 모양(snake_case) 그대로** 저장한다. 검증·변환은 읽을 때 기존 함수로.
- **바뀐 것만 받기**: `(updated_at, id)` 키셋 커서로 1000개씩. 지운 줄이 내려오면 사본에서 뺀다.
- 조회 함수는 "동기화 시도 → 사본에서 읽기". 동기화는 표마다 한 번에 하나, 5초 안 재호출은 건너뛴다.
- 읽기는 네트워크를 기다리지 않는다: 오프라인이면 동기화를 부르지 않고, 온라인이어도 **3초까지만** 기다린 뒤 사본으로 그린다. 늦게 끝나면 이벤트로 다시 그린다.
- 계정마다 다른 IndexedDB 이름.

### 쓰기: 온라인이어도 항상 사본 + 대기열(outbox)

- 모든 기록 쓰기는 사본과 대기열을 **한 트랜잭션**으로 바꾸고 바로 끝난다. 보내기는 뒤에서, 순서대로, id 기준 upsert.
- 네트워크 실패는 대기열에 남겨 연결되면 자동으로 보낸다. 서버 거절은 그 기록만 멈추고 "다시 시도"를 알린다.
- 루틴 체크 충돌은 먼저 생긴 줄로 합친다. 루틴 규칙 만들기·수정은 온라인 전용.

## 대안과 버린 이유

### 읽기

- **TanStack Query 캐시를 IndexedDB에 저장(persistQueryClient)**: 쿼리 단위 캐시라 "한 번도 안 연 11월은 오프라인에서 빈 달"이 되고, 검색처럼 조건이 매번 다른 조회는 저장되지 않는다. 기록 전부를 보관하기로 한 결정과 맞지 않는다.
- **앱 값 모양(camelCase)으로 저장**: 스키마가 바뀔 때마다 사본 마이그레이션이 필요하다. 서버 줄 그대로면 사본은 단순 복사본이다.
- **offset 페이지네이션**: 받는 사이에 줄이 바뀌면 건너뛰거나 겹친다. 키셋은 정렬 키 기준이라 안정적이다.
- **`updated_at`만 커서**: 한 트랜잭션의 줄(예: 예시 기록 12개)은 시각이 같아 페이지 경계에서 빠진다(통합 테스트로 확인).
- **Supabase Realtime 구독**: 웹소켓 연결을 유지해야 하고, 오프라인 동안 놓친 변경은 결국 커서 동기화가 필요하다. 개인 기록 앱이라 화면을 열 때 받아도 충분하다.
- **요청마다 AbortController 시간 제한**: 요청마다 신호를 넘겨야 하고, 첫 동기화(전체 받기)는 3초보다 오래 걸릴 수 있어 끊으면 안 된다. 그래서 "기다림만 3초, 요청은 계속"으로.

### 쓰기

- **온라인이면 서버에 바로, 오프라인일 때만 대기열**: 길이 둘이라 테스트·버그가 두 배이고, "온라인인데 요청이 멈춤"(실제로 겪음)을 다시 따로 처리해야 한다. `navigator.onLine`은 인터넷이 된다는 보장이 아니라 어느 길로 갈지 정하는 기준으로 믿을 수 없다.
- **Background Sync API(서비스 워커가 보냄)**: 사파리(아이폰)가 지원하지 않는다. 앱이 열려 있을 때 보내는 것으로 충분하다.
- **충돌 시 필드 단위 병합**: "마지막 저장 우선"을 지킨다(개인 기록 앱).

## 결과

- 단위 테스트(fake-indexeddb): 커서·겹침·지운 줄 빼기·페이지 이어 받기·동시 호출 묶기, 저장 → 사본·대기열, 지우기·되돌리기, 네트워크 실패·서버 거절·다시 시도, 중간 결과로 덮지 않음.
- 통합 테스트(로컬 Supabase): 같은 시각 5줄을 2개씩 받아도 빠지거나 겹치지 않음, 지운 줄도 내려옴.
- E2E: 오프라인에서 기록 탭에 기록이 보이고 검색이 사본에서 찾는다. 오프라인에서 저장 → 구름 표시 → 연결되면 사라짐.
- 성능: 처음 가는 달로 넘기기 1.2초 → 0.07초, 다시 방문 첫 표시 6.4초 → 1.1초 ([performance.md](../performance.md)).

## 감수한 것

- 동기화는 화면에서 조회할 때만 일어난다. 다른 기기의 변경은 화면을 다시 열 때 들어온다.
- 커서 60초 겹침은 경험적 값이다. 60초보다 오래 걸린 트랜잭션의 변경은 놓칠 수 있다. (이 겹침이 대량 입력 뒤 매번 다시 받는 문제를 만들어, 나중에 "커서 확정"으로 보완했다 — [트러블슈팅](../troubleshooting/2026-10-24-sync-overlap-refetch.md).)
- 저장이 늘 "성공"으로 끝나서, 서버 거절은 저장 뒤에 알게 된다. 서버 검증과 앱 검증이 다르면 거절된 기록이 기기에만 남고 "다시 시도"로만 풀린다.
- 사본은 암호화하지 않는다(브라우저 저장소). 로그아웃 때 지운다.
