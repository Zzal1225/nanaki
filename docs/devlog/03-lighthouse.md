# Lighthouse 74점에서 95점까지 — 용량을 줄인 것보다 "무엇이 LCP로 잡히나"가 컸다

> 2026-10-27 · PR #139 ~ #143 · 성능 점수 로그인 **87 → 99**, 홈 **74 → 95**, 기록 탭 **74 → 92**

## 세 줄 요약

- 배포 주소의 모바일 성능 점수를 세 화면 모두 **90점 이상**으로 올리는 것이 목표였습니다.
- 처음 계획은 "글꼴 → JS → 데이터 요청" 순서였는데, 코드를 고치기 전에 **측정으로 원인을 먼저 확인**하고 순서를 바꿨습니다.
- 가장 크게 움직인 것은 JS 용량을 줄인 것이 아니라, **측정 도구가 엉뚱한 글자를 "가장 큰 요소"로 잡던 문제**를 바로잡은 것이었습니다. 효과가 없던 시도도 그대로 적습니다.

## 먼저, 점수는 어떻게 매겨지나

Lighthouse는 구글이 만든 웹 성능 채점 도구입니다. 점수에서 가장 비중이 큰 항목이 **LCP**인데, "화면에서 가장 큰 글자나 그림이 그려진 시각"입니다. 사용자가 "아, 화면이 떴다"고 느끼는 순간을 숫자로 잡으려는 것입니다.

한 가지 함정이 있습니다. 모바일 모드의 LCP는 실제로 그려진 시각이 아니라, **그 시각 전에 시작된 모든 요청을 느린 4G·느린 폰에서 다시 받는다고 가정해 계산한 추정값**입니다. 그래서 "화면이 늦게 그려진다"보다 "**가장 큰 요소가 그려지기 전에 받는 것이 많다**"가 점수를 깎습니다. 이 사실이 이 글 전체의 열쇠입니다.

## 무슨 일이 있었나

지원을 시작하기 전, 배포 주소를 같은 조건으로 쟀습니다. 모바일 모드, 매번 새 프로필과 빈 캐시(처음 방문), 화면마다 3번 재서 가운데 값입니다.

| 화면    | 성능 점수 | 추정 LCP  | 실제로 그려진 시각 |
| ------- | --------- | --------- | ------------------ |
| 로그인  | 87        | 3.7~4.2초 | 0.3~2.3초          |
| 홈      | 74        | 6.3~6.4초 | 0.5~0.6초          |
| 기록 탭 | 74        | 6.7~7.3초 | 0.6~0.7초          |

실제로는 0.5초에 그려지는 화면이 추정으로는 6초가 넘었습니다. 그려지기 전에 받는 것이 많다는 뜻입니다.

## 처음 생각은 틀렸다

처음에는 **글꼴 → JS → 데이터 요청** 순서로 줄이려 했습니다. 웹 글꼴이 92조각이나 되고 JS도 457KiB라, 눈에 보이는 큰 것부터 치울 생각이었습니다.

그 전에 "무엇을 막으면 얼마나 줄어드나"를 측정 도구의 요청 차단 기능으로 먼저 실험했습니다.

| 막은 것             | 홈 추정 LCP        | 기록 탭 추정 LCP       |
| ------------------- | ------------------ | ---------------------- |
| 없음                | 6.3~6.4초          | 6.7~7.3초              |
| 웹 글꼴             | 5.2~5.3초 (−1.0초) | 5.5~5.7초 (−1.3초)     |
| 서버(Supabase) 요청 | 5.1~5.4초 (−1.0초) | **2.1~2.6초 (−4.6초)** |

기록 탭은 서버 요청이 압도적이었습니다. 그래서 순서를 **데이터 요청 → 글꼴 → JS**로 바꿨습니다. 코드를 한 줄 고치기 전에 순서가 바뀐 것입니다.

## 다섯 단계, 효과 없던 것부터

### 1단계. 서버에 미리 연결해 두기 → 효과 0 (#139)

데이터 요청이 크니, 서버와의 연결을 화면이 뜨자마자 미리 맺어 두면 빨라질 거라 생각했습니다. 결과는 홈 74 → 75, 추정 LCP는 그대로. **효과 없음**으로 적었습니다.

이유를 나중에 알았습니다. 데이터 요청은 JS를 다 받아 실행한 뒤에야 나갑니다. 연결을 앞당겨도 "JS 457KiB를 받는 시간"이 그 앞을 막고 있어 계산이 거의 같습니다. 실험에서 서버 요청을 막았을 때 크게 줄어든 것은 연결 때문이 아니라, **데이터를 기다리던 금액 글자가 아예 안 그려져서** LCP가 다른 요소로 당겨졌기 때문이었습니다. 실제 사용자에게는 손해가 없어 되돌리지는 않았습니다.

### 2단계. 글꼴 → 원인만 확인하고 미룸

글꼴 92조각의 선언이 화면을 막는 CSS 안에 있었습니다. 고치는 방법은 두 가지였는데 둘 다 버렸습니다. 조각 파일 이름에 빌드마다 바뀌는 값이 붙어 미리 받기를 걸 수 없었고, 글꼴을 기다리지 않는 설정은 첫 방문 화면의 "nanaki" 로고가 기본 글꼴로 보여 첫인상이 바뀝니다. 효과가 0.15초 수준인 것도 있어 **측정 흔들림 안**이라 고치지 않았습니다.

### 3-1단계. 로그인 화면이 안 쓰는 코드를 빼기 (#140)

로그인 화면은 버튼 두 개뿐인데 서버 연결·검증·기기 저장소 코드 143KiB를 처음부터 받고 있었습니다. "체험하기" 버튼이 예시 기록을 넣는 코드를 맨 위에서 불러와 함께 실린 것입니다. 버튼을 **누를 때** 받도록 바꿨습니다.

로그인 JS 353 → 206KiB, 점수 84 → 88. 줄긴 했는데 3번 측정이 95 / 87 / 88로 들쭉날쭉했습니다. 87·88점 보고서를 열어 보니 가장 큰 요소가 큰 "nanaki" 로고가 아니라 **"나는 나를 키운다" 문구의 "는" 한 글자**였고, 그 글자가 2.4초에 그려진 것으로 잡혀 있었습니다.

### 3-1b단계. 로고가 "가장 큰 요소"로 안 잡히던 이유 (#141)

측정 도구는 마지막 LCP 요소 하나만 보여 줍니다. 그래서 브라우저를 직접 조종해 **LCP 후보가 바뀌는 순서 전체**를 기록했습니다.

| 조건                  | 결과                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------- |
| 느린 망 + 느린 폰     | 3회 모두 로고                                                                         |
| 제한 없음 (빠른 환경) | 5회 중 1회만 로고. 나머지 4회는 **로고가 후보에 아예 없고** "나" → "나" → "는"(2.4초) |

예상과 반대였습니다. 환경이 **빠를수록** 문제가 생겼습니다.

원인은 등장 애니메이션이었습니다. 로고는 **투명도 0**에서 시작해 0.6초 동안 나타납니다. 그런데 Chrome은 처음 그릴 때 완전히 투명한 요소를 후보에서 빼고, 나중에 보이게 돼도 다시 세지 않습니다. 글꼴이 늦게 오면 글꼴을 바꿔 다시 그리는 순간 로고가 보이는 상태라 후보가 되지만, 글꼴이 빨리 오면 로고는 끝까지 빠집니다. 그다음 "처음 그려지는" 것이 문구 애니메이션이 1.7~2.4초에 다시 그리는 작은 글자들이었습니다.

사용자는 0.1초부터 로고를 보고 있는데, 측정은 2.4초의 "는"을 보고 그 전에 받은 JS를 전부 계산에 넣었던 것입니다.

고친 것은 한 줄입니다. 로고만 투명도 **0.01**에서 시작하게 바꿨습니다. 눈으로는 같습니다. 문구와 버튼은 0 그대로 두었는데, 거의 투명한 글자가 보이면 접근성의 대비 검사가 그 순간을 잡아 점수가 떨어질 수 있어서입니다.

결과는 로그인 88 → **98**. 그리고 뜻밖의 덤이 있었습니다. 로그인 뒤 앱을 열 때의 로딩 화면이 같은 로고를 써서, 손대지 않은 **홈이 76 → 92**가 됐습니다.

### 3-2단계. 오류 수집 도구를 첫 화면 뒤로 (#142)

오류 수집 도구(Sentry) 80KiB가 모든 화면의 첫 묶음에 실려 있었습니다. 화면이 다 뜬 뒤 한가할 때 받도록 바꾸고, 그 전에 난 오류는 모아 두었다가 켜지면 보내게 했습니다.

함정이 하나 있었습니다. 패키지를 통째로 나중에 받게 하니 번들러가 어떤 기능을 쓸지 몰라 화면 녹화·피드백 위젯까지 담아 **192KiB**가 됐습니다. 쓰는 함수 세 개만 다시 내보내는 파일을 거치니 78KiB로 돌아왔습니다. 로그인 98 → 99, 홈 92 → 94.

### 3-3단계. 기록 탭, 데이터를 기다리지 않는 자리로 (#143)

기록 탭만 75점에서 꼼짝하지 않았습니다. 이 화면의 가장 큰 요소는 **이번 달 금액**(28px 숫자)인데, 데이터가 와야 그려집니다. 그 전에 시작된 JS와 서버 요청이 전부 계산에 들어갔습니다.

3-1b와 같은 원리로 풀었습니다. 불러오는 동안 회색 상자만 그리던 카드를, 처음부터 **같은 카드 틀**(아이콘·타입 이름·값 자리의 흐린 줄표)로 그려 두고 데이터가 오면 글자만 바꿉니다. Chrome은 이미 그린 글자의 내용이 바뀌는 것은 다시 세지 않습니다. 기록 탭 75 → **92**.

정직하게 적어 둘 것이 있습니다. 첫 방문에 금액이 실제로 보이는 시각은 그대로입니다. 바뀐 것은 측정이 가리키는 대상이고, 사용자가 보는 것은 회색 상자 대신 카드 틀입니다. 다시 방문은 기기 사본에서 읽어 원래 빠릅니다.

성능 90+는 세 화면 모두 달성했고, LCP 2.5초 미만은 로그인만 달성했습니다. 홈·기록 탭에 남은 0.2~0.4초는 화면 틀이 그려지기 전에 받는 HTML·CSS·앱 틀 JS입니다. 그중 큰 덩어리인 데이터 코드(약 140KiB)는 오프라인 우선 구조상 첫 화면부터 기기 사본을 읽어야 해서 뒤로 미룰 수 없습니다. 실험실 점수를 위해 실제 사용자의 체감을 늦추는 거래라 거기서 멈췄습니다.

## 배운 것

- **고치기 전에 "무엇을 막으면 얼마나 줄어드나"를 잰다.** 그 실험 하나로 작업 순서가 바뀌었고, 1단계가 왜 효과가 없었는지도 설명됐습니다.
- **점수는 용량보다 "무엇이 언제 가장 큰 요소로 잡히나"에 민감했다.** JS 147KiB를 줄여 +4점, 투명도 한 줄을 고쳐 +10점과 +16점이었습니다.
- **도구가 보여 주는 결과 하나보다 과정 전체를 본다.** "왜 이 글자가 LCP인가"가 아니라 "왜 로고가 LCP가 아닌가"가 답이었고, 후보 목록 전체를 찍어야 보였습니다.
- **한 번 적어 둔 원인도 가설이다.** "글꼴이 늦어서"라고 기록해 둔 원인은 조건을 바꿔 재 보니 반대였습니다.
- **효과 없는 시도도 기록한다.** 1단계와 2단계를 지우면 "다섯 번 다 맞힌 사람"처럼 보이지만, 다음 사람이 같은 길을 다시 걷습니다.

## 다시 한다면

등장 애니메이션을 넣던 날(Issue #9)에 LCP 후보를 한 번 찍어 봤을 것입니다. 그때 "투명도 0에서 시작하면 후보에서 빠진다"를 알았다면, 3-1b는 트러블슈팅이 아니라 설계 메모 한 줄이었을 것입니다. 보이는 것을 바꾸는 작업은 측정 도구가 보는 것도 함께 바꾼다는 사실을 이제는 기본으로 둡니다.
