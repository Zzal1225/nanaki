# 자동화할 것과 아이폰에서만 볼 것을 나누기 — 아이폰 버그 6건 중 3건은 이미 있던 도구로 잡을 수 있었다

> 2026-10-22 · PR #76부터 · 자동 테스트 단위 855 · 통합 70 · E2E 33 · 실기기 확인은 체크리스트 10분

## 세 줄 요약

- 2단계를 마치고 아이폰에서 직접 써 보니 버그가 **6건** 나왔습니다. 자동 테스트는 모두 초록불이었는데도요.
- 따져 보니 그중 **3건은 이미 있던 도구로 잡을 수 있었습니다.** 도구가 모자란 게 아니라 **테스트하는 방식**이 문제였습니다.
- 그래서 선을 그었습니다. 자동화할 수 있는 것은 전부 자동 테스트로, **정말 기기에서만 보이는 것**만 사람이 10분 체크리스트로 봅니다.

## 무슨 일이 있었나

nanaki는 휴대폰 홈 화면에 설치해 쓰는 앱입니다. 그래서 단계를 마칠 때마다 실제 아이폰에서 써 봅니다. 2단계 뒤 확인에서 나온 문제는 이랬습니다.

- 닫았다 다시 연 작성 화면이 홈으로 튕김
- 오프라인에서 로그아웃이 됨
- 입력칸을 누르면 화면이 확대됨
- 키보드 위에 하단 탭이 떠 있음
- 맨 위 글자가 상태 표시줄(시계·배터리)과 겹침
- 아직 안 보낸 기록을 뜻하는 구름 아이콘 문제

자동 테스트는 전부 통과한 상태였습니다. "역시 아이폰은 직접 봐야 해"로 끝낼 수도 있었습니다.

## 처음 생각은 틀렸다

처음에는 여섯 건 모두 "아이폰이라서 생기는 문제"라고 생각했습니다. 그런데 하나씩 따져 보니 **3건은 PC의 크롬과 이미 있던 자동 테스트 도구(Playwright)로 잡을 수 있는 종류**였습니다. 아이폰 고유의 문제가 아니라, 테스트가 그 길을 걷지 않았을 뿐이었습니다.

왜 못 잡았을까요. 테스트 **방식** 세 가지가 원인이었습니다.

1. **화면을 매번 새로 열었습니다.** 자동 테스트가 화면마다 주소를 직접 쳐서 들어갔기 때문에, 화면을 **오갈 때만** 생기는 문제를 지나쳤습니다. 사람은 앱 안에서 버튼을 눌러 이동합니다.
2. **실패 상황은 가짜 환경에서만 봤습니다.** 서버 오류나 저장 거절은 작은 단위 테스트로만 확인했고, 실제 브라우저에서 그 화면이 어떻게 보이는지는 보지 않았습니다.
3. **기능 흐름 테스트가 전부 PC 크기(1280px)였습니다.** 휴대폰 크기와 손가락 터치로 도는 테스트가 없었습니다.

## 어떻게 나눴나

기준은 하나였습니다. **"이 문제는 컴퓨터가 흉내 낼 수 있는가?"**

|      | 자동 테스트가 맡는 것                                                                                                                     | 사람이 아이폰에서 보는 것                                                                                                           |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 기준 | 크기·터치·네트워크처럼 컴퓨터가 흉내 낼 수 있는 조건                                                                                      | 홈 화면 앱·실제 키보드·상태 표시줄처럼 흉내 낼 수 없는 것                                                                           |
| 예   | 입력칸 글자 16px 이상(확대 방지), 가로 넘침, 터치 영역 44px, 입력 중 하단 탭 숨김, 화면을 오가며 쓰기→상세→수정→삭제, 서버 오류·느린 응답 | 글자가 상태 표시줄과 겹치는지, 하단 탭이 홈 막대 위에 있는지, 실제 키보드가 올라올 때, 홈 화면 앱에서 로그인, 카메라·파일 선택·인쇄 |
| 언제 | 모든 PR, 통과 못 하면 병합 불가                                                                                                           | 레이아웃·입력·서비스 워커·로그인을 건드린 PR 뒤, 그리고 단계 마무리 때. 약 10분                                                     |

구체적으로 세 가지를 했습니다.

- **아이폰 크기·터치로 도는 자동 테스트**를 새로 만들었습니다(PR #76). 주소를 치지 않고 앱 안을 눌러 이동하고, 화면마다 "아이폰 단골 함정" 세 가지를 자동으로 검사합니다. 입력칸 글자 16px 이상, 가로 넘침 없음, 터치 영역 44px 이상.
- **실기기 체크리스트**를 만들었습니다. 자동화할 수 없는 것만 적어 약 10분 분량입니다. 같은 종류의 문제가 기기에서 다시 나오면, 자동화할 수 있는지 먼저 보고 자동 쪽으로 옮깁니다.
- 이어서 **실패 상황 테스트**(서버 응답을 바꿔 치기)와 **사파리 엔진(WebKit) 테스트**를 더했습니다. WebKit은 처음에 경고만 하다가, 최근 50회 실행이 모두 통과한 것을 근거로 2026-10-26부터 실패하면 병합을 막도록 바꿨습니다.

## 고르지 않은 것들

- **실기기 클라우드(BrowserStack 등)**: 진짜 아이폰을 빌려 쓸 수 있지만 새 도구이고 유료입니다. 1인 프로젝트 규모에 과했습니다.
- **상태 표시줄 여백을 코드로 흉내 내기**: 흉내가 실제와 맞는지 확인할 방법이 없는 추측이라, 체크리스트로 넘겼습니다.
- **요청 가로채기 라이브러리(MSW) 도입**: 실제 브라우저 테스트는 Playwright의 응답 바꾸기로, 단위 테스트는 저장 함수 가짜로 충분했습니다.
- **모든 PR마다 실기기 확인**: 손이 많이 들어 지속하지 못합니다. 직접 겪었습니다. 몰아서 봅니다.

## 감수한 것

- **WebKit 테스트는 리눅스의 WebKit**이라 아이폰 사파리와 같지 않습니다. 홈 화면 앱·실제 키보드처럼 기기에서만 생기는 문제는 여전히 사람이 봅니다.
- **"의도한 변경에 테스트를 맞추는" 비용**이 있습니다. CI 실패 19번 중 16번이 그것입니다. 화면을 바꾸면 기준 이미지를 다시 찍고 커밋해야 합니다. 대신 바뀌지 않아야 할 화면이 바뀌면 바로 압니다.

## 배운 것

- **"기기에서만 생기는 문제"라는 말을 의심한다.** 여섯 건 중 셋은 그냥 테스트가 그 길을 안 걸었을 뿐이었습니다. 도구를 더 사기 전에 방식을 먼저 봅니다.
- **사람이 할 일은 적어 둬야 지속된다.** "꼼꼼히 보기"는 지속되지 않았고, "10분짜리 목록"은 지속됐습니다. 그리고 목록에서 자동 쪽으로 옮기는 규칙이 있어야 목록이 줄어듭니다.
- **통과하는 테스트도 점검한다.** 낡은 기준 이미지 24장은 매번 초록불이었습니다. 허용치를 0으로 바꿔 보는 식으로 "이 테스트가 정말 보고 있나"를 가끔 확인합니다.
- **숫자를 세어 두면 다음 결정이 쉽다.** 17건 중 11건이 기기 전용이라는 숫자가 있으니 "실기기 확인을 없애자"도 "매 PR마다 하자"도 아닌 "몰아서 하자"를 자신 있게 고를 수 있었습니다.

## 다시 한다면

첫 자동 테스트를 만들 때부터 **휴대폰 크기로, 앱 안을 눌러 이동**하게 했을 것입니다. 주소를 직접 쳐서 PC 크기로 들어가는 테스트는 쓰기 쉽지만 사용자가 걷는 길이 아닙니다. 그 두 가지만 처음부터 지켰어도 여섯 건 중 셋은 아이폰을 들기 전에 잡혔을 것입니다.
