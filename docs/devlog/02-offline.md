# 한 번도 안 연 화면을 오프라인에서 열기 — CI가 다섯 번 실패했고, 원인은 다섯 번 다 달랐다

> 2026-10-22 · PR #70 · 기록 상세 주소를 `/records/<id>`에서 `/records/view?id=<id>`로 바꾼 이유

## 세 줄 요약

- nanaki는 인터넷이 끊겨도 **한 번도 열어 본 적 없는 화면**까지 열리는 것을 목표로 했습니다.
- 미리 받아 두면 될 줄 알았는데 자동 테스트가 **다섯 번 연속** 실패했고, 고칠 때마다 다음 실패의 원인이 달랐습니다.
- 가장 큰 원인은 **주소 모양**이었습니다. 기록 번호를 주소 경로에서 빼고 `?id=` 꼬리표로 옮기자, 화면 틀 한 장으로 모든 기록이 열렸습니다.

## 무슨 일이 있었나

nanaki는 지하철이나 비행기에서도 쓸 수 있어야 합니다. 그래서 "오프라인 우선"으로 만들었습니다. 기록은 기기 안에 사본을 두고, 화면 틀은 앱 안의 **창고지기(서비스 워커)**가 미리 받아 둡니다.

여기서 욕심을 하나 더 냈습니다. 이미 열어 본 화면만이 아니라, **한 번도 연 적 없는 화면**도 열리게 하자. 예를 들어 오프라인에서 어제 쓴 기록을 처음 눌러도 상세 화면이 나와야 하고, 운동 기록을 한 번도 안 써 봤어도 작성 화면이 열려야 합니다.

방법은 단순해 보였습니다. 로그인 직후, 창고지기가 상세·수정·타입별·작성 화면의 틀을 미리 받아 두면 끝. 그런데 실제 브라우저로 돌리는 자동 테스트(E2E)가 다섯 번 연속 빨간불이었습니다.

## 처음 생각은 틀렸다

처음에는 "미리 받는 코드에 작은 실수가 있겠지"라고 생각했습니다. 한 군데만 고치면 될 줄 알았습니다.

하나를 고치면 테스트는 **다른 자리에서** 실패했습니다. 다섯 번의 실패는 다섯 가지 다른 원인이었고, 그중 둘은 "통과했다"고 보고하면서 실제로는 아무것도 확인하지 않은 가짜 통과였습니다.

## 원인을 찾은 방법: 실패한 자리에서 "진짜 상태"를 찍어 보기

코드를 읽어서는 답이 안 나왔습니다. 그래서 테스트가 실패하는 바로 그 순간에, 창고지기가 **실제로 무엇을 받아 두었는지** 보관함 목록을 출력하게 했습니다.

목록에는 방문한 두 화면만 있었습니다. "미리 받기"가 돌긴 했는데 **아무것도 받지 않은** 것입니다. 여기서부터 원인이 하나씩 드러났습니다.

## 다섯 번의 실패, 다섯 가지 원인

### 1. 주소에 기록 번호가 있으면 화면 틀 한 장을 돌려쓸 수 없다 (설계)

기록 상세 주소가 `/records/기록번호` 모양이었습니다. 창고지기는 기록 하나의 상세 화면 틀을 받아 두고, 다른 기록을 열 때 그 틀을 돌려쓰려 했습니다. 그런데 화면은 "기록을 여는 중…"에서 멈췄습니다.

비유하면 **이름이 인쇄된 초대장**입니다. 경로에 들어간 번호는 화면 틀 안에 같이 찍혀 있어서, 다른 기록 주소에 가져다 쓰면 "초대장의 이름과 다르다"며 멈춥니다.

→ 주소를 `/records/view?id=기록번호`로 바꿨습니다. `?` 뒤의 꼬리표는 화면 틀에 찍히지 않습니다. 틀은 **이름 칸이 빈 초대장** 한 장이 되고, 브라우저가 열 때 꼬리표를 읽어 이름을 채웁니다. 예전 주소로 들어오면 새 주소로 자동으로 넘겨서 기존 링크도 살렸습니다.

### 2. "이미 받았나?" 확인이 엉뚱한 것을 찾았다 (앱)

미리 받기 전에 "이미 보관함에 있나?"를 확인하는데, 그 확인이 **주소의 꼬리표를 무시하고** 찾도록 되어 있었습니다. 그러자 프레임워크가 따로 받아 둔 화면 조각 데이터가 "있다"로 잡혀서, 모든 화면을 이미 받은 것으로 착각하고 건너뛰었습니다.

→ 주소를 글자 그대로 비교하고, 화면 틀은 직접 요청해서 받도록 바꿨습니다.

### 3. 테스트가 "통과"라고 했지만 아무것도 기다리지 않았다 (테스트)

"미리 받기가 끝날 때까지 기다렸다가 오프라인으로 바꾼다"는 코드가 있었는데, 기다리는 함수에 넘긴 값의 모양이 잘못돼 **항상 즉시 참**으로 끝났습니다. 받기가 끝나기도 전에 오프라인으로 바꾸고 있었던 것입니다.

→ 조건이 참이 될 때까지 반복해서 확인하는 방식(`expect.poll`)으로 바꿨습니다.

### 4. 커밋에 파일이 빠졌다 (작업 실수)

지운 폴더 경로를 함께 add하는 바람에 add 전체가 실패했는데 그대로 커밋했습니다. 파일 이동만 올라가고 고친 코드는 빠진 채 CI가 돌았습니다.

→ 다시 커밋. 부끄럽지만 "다섯 번" 중 하나라 그대로 적습니다.

### 5. 열 때마다 서버가 일부를 그리는 화면은 저장본으로 열면 멈춘다 (설계)

타입별 화면(`/records/type/가계부` 등)은 일부를 **요청이 올 때 서버가 그리는** 방식이었습니다. 저장본으로 열면 서버가 그려 줄 부분이 비어서 거기서 멈췄습니다.

→ 타입이 다섯 개뿐이니 빌드할 때 다섯 장을 모두 미리 그려 두는 **정적 화면**으로 바꿨습니다.

## 왜 주소까지 바꿔야 했나

- **그 전 단계는 "한 번이라도 연 화면"만 오프라인에서 열렸습니다.** 거기서 멈출 수도 있었지만, "어제 쓴 기록을 지하철에서 처음 열기"가 안 되면 오프라인 우선이라는 앱의 약속이 반쪽이 됩니다.
- **창고지기는 화면을 주소별로 저장합니다.** 주소에 들어간 값을 서버가 읽어 화면 틀에 넣으면 값마다 틀이 달라져, 기록이 1만 건이면 틀도 1만 장이 필요합니다. 틀을 한 장으로 만들려면 값을 서버가 아니라 **브라우저가 읽어야** 하고, 그러려면 값이 경로가 아니라 `?` 뒤에 있어야 했습니다.
- 주소가 바뀌는 일이라 혼자 정하지 않고 확인을 받은 뒤 바꿨고, 예전 주소는 자동으로 새 주소로 넘어가게 해서 기존 링크를 지켰습니다.

미리 받아 두지 않는 화면은 전처럼 오프라인 대체 화면이 나옵니다. 이 일 뒤로 두 가지가 프로젝트 규칙이 됐습니다. **오프라인에서 저장본으로 열 화면은 정적이어야 하고, 주소에 담긴 값은 서버가 아니라 브라우저가 읽는다.** 창고지기가 미리 받을 화면 목록은 한 파일에만 둡니다.

## 배운 것

- **"통과"를 믿지 말고 상태를 본다.** 다섯 번 중 두 번은 확인 코드가 아무것도 확인하지 않은 채 통과하고 있었습니다. 의심스러우면 실패 지점에서 실제 상태(보관함 목록)를 찍어 보는 것이 코드를 읽는 것보다 빨랐습니다.
- **실패 한 번에 원인 하나라고 가정하지 않는다.** 하나를 고친 뒤의 다음 실패는 다른 원인일 수 있습니다. "아까 고쳤는데 왜 또?"가 아니라 "이번엔 뭐지?"로 봐야 했습니다.
- **오프라인은 주소 설계부터 정해진다.** 화면 틀 한 장을 돌려쓰려면 주소에 데이터를 넣으면 안 됩니다. 이건 나중에 고치기 가장 비싼 종류의 결정이라, 처음부터 정해 두는 편이 좋습니다.

## 다시 한다면

"한 번도 안 연 화면도 열린다"를 목표로 세운 날, 코드를 쓰기 전에 **화면 틀이 몇 장 필요한지**부터 셌을 것입니다. 그 질문 하나로 1번 원인(주소 설계)과 5번 원인(서버가 그리는 화면)은 시작 전에 걸러졌습니다. 나머지 셋은 테스트가 잡아 줬을 것이고요.
